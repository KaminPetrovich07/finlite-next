# FinLite KG — Next.js / PostgreSQL (миграция, Phase 1)

Это фундамент новой архитектуры поверх текущего `app.py`. Не полный перенос
2541 строки Streamlit — это нереалистично сделать качественно за один присест.
Ниже честно: что готово, что проверено, что осталось.

## Фаза 3: план счетов №231, налоги по НК КР, дизайн, ESG, выгрузка

- **План счетов** (`lib/ledger/accounts.ts`) — все счета Инструкции, утв. постановлением
  Правительства КР от 7.10.2010 № 231, с официальными кодами и названиями. ОПиУ по разделам
  6000–9900, закрытие периода через 5999 на 5300 (`/api/ledger/close`).
- **Налоги** (`lib/tax-engine.ts`, `REGIME_INFO`) сверены с Налоговым кодексом в ред. от
  06.08.2026: общий режим с налогом с продаж 1% / 2% (ст. 368), все ставки единого налога
  ст. 423 (0,5%; 4/2%; 6/4%; общепит 5% / 3%; швейное и текстильное 0,25%; 0,1%; 0%),
  налог на электронную торговлю 2%, патент. Режима «упрощённый 2%» в Кодексе нет — удалён.
  Страховые взносы: 2,25% работодатель + 10% работник; начисление зарплаты одной проводкой
  (`/api/ledger/payroll`).
- **Дизайн**: светлая тема по умолчанию и тёмная, переключатель в меню; все цвета — CSS-переменные
  (`app/globals.css`), шрифты Manrope и IBM Plex Sans ставятся из npm (`@fontsource`), без
  обращения к Google Fonts при сборке. Графики на странице отчётности (палитра проверена на
  различимость при дальтонизме).
- **ESG** (`/esg`, `lib/esg.ts`): выбросы Scope 1/2, энергия, вода, отходы, персонал, органы
  управления, GRI 201-1. Денежные показатели — из журнала, нефинансовые — форма (модель `EsgReport`).
- **Выгрузка** (`/packages`, `/api/export`): пять пакетов — полная отчётность, для руководителя,
  для аудитора, управленческий, ESG — в PDF, Word и Excel из одной модели документа
  (`lib/reports`).
- `npm test` — 20 тестов.

**После обновления:** `npx prisma db push` (новая таблица `EsgReport`, изменения только добавляющие).
Старые проводки с кодами прошлой версии (6010, 7220 и т.п.) сверка покажет как «нет в плане
счетов» — удалите их или создайте заново копию демо-компании.

## Журнал проводок и связанная отчётность (фаза 2)

Все формы теперь строятся из одного источника — журнала проводок
(`JournalEntry` / `JournalLine` в Prisma). В отчёты ничего не вводится руками,
поэтому они не могут разойтись между собой.

```
выписка / ручная проводка / начальные остатки / начисление налогов
        └──► журнал ──► ОСВ ──► Баланс Ф.1 · ОПиУ · ОДДС Ф.3 · Капитал Ф.4 · Налоги
                                  └──► автоматические сверки между формами
```

- `lib/ledger/accounts.ts` — план счетов; каждый балансовый счёт привязан к строке Ф.1,
  каждый счёт 6xxx/7xxx — к статье ОПиУ, каждому задана роль в ОДДС.
- `lib/ledger/engine.ts` — чистые функции: ОСВ, ОПиУ, баланс на начало и конец (прибыль
  закрывается в стр. 530 виртуально), ОДДС прямым методом по корреспондирующему счёту,
  отчёт о капитале, налоги, сверки. Без Prisma — тестируется напрямую.
- `lib/ledger/taxes.ts` — начисление налогов из оборотов периода; ставки берутся из
  `lib/tax-engine.ts`. Для единого налога наличная/безналичная часть берётся из
  фактических поступлений (касса 1110 vs остальное), а не из ползунка.
- `lib/ledger/posting.ts` — категория банковской операции → проводка. Импорт выписки и
  смена категории сразу проводятся в журнал.
- Сверки: Дт = Кт в каждой проводке; ОСВ; актив = пассив; ОДДС стр. 710 = баланс стр. 110+120;
  Ф.4 стр. 120 = баланс стр. 541; Ф.4 стр. 080 = чистая прибыль; налоги начислены и совпадают
  с расчётом; нет невыясненных сумм; все операции выписки проведены.
- Страницы: `/reports` (отчётность с расшифровкой каждой строки до проводок) и `/ledger`
  (журнал, ручные проводки, начальные остатки). Демо-компания `companyId=demo` работает без БД.
- Тесты: `npm test` — 12 тестов, включая 200 случайных журналов, на которых все сверки
  обязаны сходиться.

**После обновления кода** выполните `npx prisma db push` — схема дополнена двумя таблицами
и полем `Company.patentAmount` (изменения только добавляющие, данные не трогаются).

## Что сделано и проверено в этой фазе

- **Налоговый движок** (`lib/tax-engine.ts`) — построчный порт `calculate()`,
  `compareRegimes()`, `breakEven()`, `safetyMargin()`, `doForecast()`,
  `validateInputs()` из app.py. **Прогнан против Python-версии на 4 сценариях
  (общий/единый/патент/упрощённый режимы) — все цифры сошлись до копейки.**
- **Prisma-схема** (`prisma/schema.prisma`) — Company / Report / BankTransaction.
  В отличие от текущего SQLite, где сохраняется только сводная строка отчёта,
  здесь персистится весь баланс/ОДДС/ФОСАМК/LeanOps через JSONB-поля — то,
  что сейчас живёт только в `st.session_state` и теряется при обновлении.
- **API-роуты**: `/api/companies`, `/api/reports` — POST всегда пересчитывает
  налоги на сервере (не доверяет цифрам с клиента), GET — замена `load_history()`.
- **Маска ввода чисел** (`lib/format.ts`, `components/MoneyInput.tsx`) —
  пробелы между разрядами при вводе, прямой фикс жалобы на спутанные нули.
- **Калькулятор-страница** (`app/page.tsx`) — компания → период → режим →
  ввод → расчёт → сохранение → история. Мобильный layout на Tailwind.
- **Импорт банковских выписок + категоризация** (`/transactions`):
  - `lib/bank-parser.ts` — парсер XLSX/CSV с автоопределением колонок по
    заголовкам (дата/сумма/назначение, варианты "Приход"+"Расход" отдельно
    или единая "Сумма" со знаком). TXT — эвристический best-effort парсер.
    **Реальных файлов выписок МБанк/Бакай Банк/Элдик под рукой не было** —
    протестировано на синтетических CSV и XLSX (оба формата колонок).
    Нужно прогнать через реальный экспорт и сообщить, если что-то не
    распозналось — список псевдонимов заголовков в начале файла легко
    расширить.
  - `lib/categories.ts` + `lib/categorize.ts` — двухпроходная категоризация:
    сначала бесплатные ключевые слова (зарплата/аренда/связь/такси и т.д.),
    оставшееся — один батч-запрос в Claude Haiku (не по одному вызову на
    транзакцию). На тесте: 5 из 8 операций определились по ключевым словам
    без единого API-вызова.
  - Ручная коррекция категории прямо в таблице (PATCH `/api/transactions`).
- **Сравнение режимов** (`/compare`) — UI поверх уже готового `compareRegimes()`,
  таблица по всем 10 режимам НК КР с подсветкой оптимального.
- **Баланс Ф.№1 / IAS 1** (`/balance`) — все ~80 строк баланса из app.py,
  сворачиваемые секции, авто-расчёт итогов (191/294/299/371/431/499/541/599)
  с проверкой зависимостей между разделами, проверка сведения баланса.
  Сохраняется в `Report.balanceSheet` через `PATCH /api/reports/[id]`.
- **ОДДС Ф.№3 / IAS 7** (`/cashflow`) — прямой метод, операционная /
  инвестиционная / финансовая деятельность, авто-каскад итогов (40→120→190→
  …→700→710), привязан к выбранному отчёту аналогично балансу.
  Логика итогов в обоих модулях прогнана на тестовых числах — каскад
  суммирования (включая итог-от-итогов вроде 299=191+294) даёт верный результат.
- **Капитал Ф.№4** (`/equity`) — изменения в собственном капитале, 4 колонки
  × 11 строк, автозаполнение чистой прибыли в "Нераспред. прибыль"/"Итого".
- **Big 4 Executive Report** (`/executive`) — сводка для руководителя:
  KPI-дашборд, флаги рисков (низкая рентабельность/убыток/высокий ФОТ/
  себестоимость/запас прочности — пороги 1:1 с app.py), CVP-график
  (recharts LineChart с точкой безубыточности), 3 сценария прогноза на
  слайдерах (песс./база/опт.), рекомендации (включая авто-расчёт экономии
  от смены налогового режима), водопад «выручка → прибыль» (recharts
  stacked-bar trick — невидимая база + цветной дельта-бар) и пояснительная
  записка IAS 1.112. Логика рисков/водопада/каскада прогнана на тестовых
  числах отдельно от UI перед сборкой.
- **LeanOps** (`/leanops`) — 4 внутренних таба:
  - Учёт остатков: расход сырья, WIP, отходы/брак, стоимость потерь.
  - Аудит 7 видов муда: слайдеры 0–10, Lean-индекс, радар-чарт (recharts),
    топ-3 приоритета.
  - Юнит-экономика: себестоимость на единицу, 6 каналов продаж с комиссией,
    водопад "цена → маржа", сравнение каналов.
  - Lean-дашборд: сводка по всем трём + интеграция с выбранным отчётом
    (сохраняет в `Report.leanResults`) + roadmap на 3 месяца.
  Все три расчётных движка прогнаны на ручных контрольных примерах перед
  сборкой UI (см. историю чата) — совпадение с ожидаемыми значениями точное.
- Билд проверен дважды: статически (`npm run build`, все 9 страниц) и
  вживую через `next dev` с реальными HTTP-запросами.

## Запуск локально

```bash
npm install
cp .env.example .env   # вписать DATABASE_URL, опционально ANTHROPIC_API_KEY
npx prisma generate
npx prisma migrate dev --name init
npm run dev
```

Без `ANTHROPIC_API_KEY` импорт выписок всё равно работает — просто всё, что
не распозналось по ключевым словам, останется как "Не определено" вместо
LLM-категоризации. Ключ берётся на [console.anthropic.com](https://console.anthropic.com).

## База данных (бесплатно)

1. Зарегистрируйся на [neon.tech](https://neon.tech) или [supabase.com](https://supabase.com)
2. Создай проект → скопируй connection string → вставь в `.env` как `DATABASE_URL`
3. `npx prisma migrate dev --name init` — создаст таблицы

Оба сервиса дают пуленный (pooled) коннекшн — это и есть решение твоей
проблемы с конкурентным доступом: Postgres сам управляет блокировками на
уровне строк, а не блокирует всю базу как SQLite на Streamlit Cloud.

## Деплой

Push в GitHub → импортируй репо на [vercel.com](https://vercel.com) →
добавь `DATABASE_URL` в Environment Variables → деплой. Аналогично тому,
как сейчас подключён Streamlit Cloud к твоему репо.
